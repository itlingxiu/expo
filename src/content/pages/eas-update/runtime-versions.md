# 运行时版本与更新

运行时版本是一项属性，用于保证构建的原生代码与更新之间的兼容性。项目被做成构建时，构建会包含一些无法用更新改变的原生代码。因此，更新必须与构建的原生代码兼容，才能在该构建上运行。

下图说明构建与更新如何相互作用：

![原生层与更新层示意图](/static/images/eas-update/layers.png)

可以把构建看成两层：构建进应用二进制文件的原生层，以及可以与其他兼容更新互换的更新层。这种分离让我们可以向构建发送 bug 修复，只要带有该修复的更新能够在构建内的原生层上运行。`"runtimeVersion"` 属性让我们可以保证某个更新与特定构建的原生代码兼容。

由于更新必须与构建的原生代码兼容，每当原生代码更新时，我们都需要先做一次新构建，然后才能发布更新。有些开发者只在升级到新的 Expo SDK 时更新原生代码，另一些人可能在两次构建之间或其他间隔升级原生代码。下面说明可能适合你项目的不同情况与配置。

## 设置 `"runtimeVersion"`

为了让构建与更新之间更容易管理 `"runtimeVersion"` 属性，我们创建了一些策略，从项目中已有的其他信息推导运行时版本。如果这些策略不符合项目的开发流程，也可以手动设置 `"runtimeVersion"`。

### 运行时版本策略

可用策略记录在 [`expo-updates` 库文档](/versions/latest/sdk/updates#使用运行时版本策略的自动配置)中。

### 自定义运行时版本

你也可以设置符合[运行时版本格式要求](/versions/latest/config/app#runtimeversion)的自定义运行时版本：

```json
{
  "expo": {
    "runtimeVersion": "1.0.0"
  }
}
```

对于希望手动管理运行时版本、并与应用配置中其他版本号分开的开发者，这个选项很合适。它让开发者完全控制哪些更新与哪些构建兼容。

### 平台特定的运行时版本

你也可以按平台设置运行时版本，例如：

```json
{
  "expo": {
    "android": {
      "runtimeVersion": "1.0.0"
    }
  }
}
```

或者：

```json
{
  "expo": {
    "android": {
      "runtimeVersion": {
        "policy": "appVersion"
      }
    }
  }
}
```

当同时设置了顶层运行时和平台特定运行时时，平台特定的那个优先。

## 避免不兼容的更新

发布更新时可能出现的主要问题是：更新依赖的原生代码，它所运行的构建并不支持。例如，假设我们做了一个运行时版本为 `"1.0.0"` 的构建，然后把该构建提交到应用商店并向公众发布。

之后，假设我们开发了一个依赖新安装的原生库（例如 `expo-camera`）的更新，并且没有更新 `"runtimeVersion"` 属性，因此它仍是 `"1.0.0"`。如果我们发布了更新，运行时版本为 `"1.0.0"` 的构建会认为这个运行时版本相同的传入更新是兼容的，并尝试加载它。由于该更新会调用构建中不存在的代码，`expo-updates` 可能会检测到错误并尝试回滚到先前可用的更新（[进一步了解错误恢复行为](/eas-update/error-recovery)）。

以下是一些策略，用来避免部署与构建原生代码不兼容的更新。

### 使用会在原生代码更新时自动更新运行时版本的策略

`"appVersion"` 策略会在应用版本递增时递增运行时版本，但如果你在更改原生运行时时忘记提升应用版本，就会出现运行时版本不匹配。如果你希望让不兼容的更新极不可能发生，代价是需要更频繁地创建构建，可以使用 `"fingerprint"` 策略。任何可能影响原生运行时的变化都会递增运行时版本（[进一步了解指纹](/versions/latest/sdk/fingerprint)）。

### 手动递增运行时版本

每当安装或更新原生代码时，在项目的[应用配置](/workflow/configuration)中[手动递增 `"runtimeVersion"` 属性](#自定义运行时版本)。

### 逐步推出更新

如果你不确定新更新的影响，可以先把它推给一小群用户。使用[灰度发布](/eas-update/rollouts)把更新发布给一小部分用户，并在 EAS 仪表盘上监控该更新的错误率。如果发现错误率很高，就取消灰度。如果已经完全推出，则[回滚](/eas-update/rollbacks)。

### 用较小的用户群手动验证更新

部署到生产环境时，创建一个使用相同运行时但指向不同 channel 的预览构建。在把更新提升到生产之前，先在这些构建上测试（更多内容见[部署指南](/eas-update/deployment#部署预览)）。你也可以让应用中的某些用户通过 [channel surfing](/eas-update/channel-surfing)选择接收该更新。
